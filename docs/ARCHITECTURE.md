# Architecture (v3)

## Principles
1. **Unknown is never zero.** Every nutrient is a number or `null`. Totals report coverage (share of calories with data). Trend rules only use a nutrient on days where ≥80% of calories have data.
2. **History is immutable.** Every diary entry stores a full nutrient snapshot of each item at log time. Editing or deleting foods or saved meals never changes past days.
3. **Nothing is invented.** No value is guessed. Missing → "unknown"; no match → "create food / quick add". OCR values are always confirmed by the user.
4. **Data never silently disappears.** Old data is copied, never deleted; unreadable data is quarantined; destructive actions take a safety snapshot first.

## Components
- **Static site on GitHub Pages**, plain ES modules, no build step, zero cost.
- **Storage:** IndexedDB `nutriledger` (beta: `nutriledger-beta`), schema v1, append-only migration list (`js/store/db.js`). Stores: meta, profiles, foods (user), meals, entries (index profileId+date), weights, days, stats, portions, snapshots. Multi-store writes are single transactions.
- **v2 migration:** on first launch, reads `localStorage["nl_mj_v2"]` (never modifies it), maps profiles/entries/meals/weights, repairs the v2 duplicate food-ID bug (Walnuts/Cashews etc.), quarantines unreadable data, runs once.
- **Food library:** generated by `tools/build-library.mjs` from vendored IFCT 2017 CSV + USDA SR Legacy (via TempoLife dataset) + curated Indian portions and 78 dish recipes. Dishes are computed from ingredient data; cooking fat is adjustable per serving.
- **Search:** every query word must match a name, alias (incl. Hindi names from IFCT) or brand, allowing one typo; personal frequency boosts ranking; diet filter (veg / egg / non-veg) per profile.
- **Packaged foods:** Open Food Facts (free, crowd-sourced) on explicit request; relevance filter + plausibility checks; products are saved to "my foods" when logged so they work offline.
- **Camera:** barcode via ZXing; label via Tesseract.js on-device with Otsu thresholding, then a parser with an energy checksum and decimal-consistency checks. All vendored; loaded only when used.
- **Analysis:** `js/core/analysis.js` — five alert classes: limit exceeded (fact), below target, persistent low (below EAR for micronutrients), persistent high, insufficient data; plus caution for sustained very low intake or rapid weight loss. Today is never judged "below target" while in progress. Sodium is only checked for excess.
- **Offline:** generated service worker precaches the app shell with a content hash; updates are offered ("Update"), never forced mid-use; the production worker ignores `/beta/`.

## Why not native iOS / cloud sync (now)
- A native app gives stronger storage guarantees but needs the Apple Developer Program (US$99/year) and a Mac. Revisit if web storage ever proves unreliable.
- Cloud sync needs an account system and a server (free tiers exist, e.g. Supabase) but adds privacy, auth and failure modes. Backups to iCloud Drive via the share sheet cover data safety at zero cost.
